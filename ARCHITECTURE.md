# Архитектура

Верхнеуровневый пайплайн и границы слоёв по структуре ТЗ (нормализация фото → извлечение признаков → поиск по каталогу → выдача карточки → дополнительный функционал). Детали каждого слоя — в доках сервисов, здесь они не дублируются: [`web/ARCHITECTURE.md`](web/ARCHITECTURE.md) (поток на сайте, функции удержания), [`ml/ML_SERVICE.md`](ml/ML_SERVICE.md) (контракт `ml/`, устройство пайплайна, данные и замеры), [`deploy/vast/README.md`](deploy/vast/README.md) (деплой на GPU).

## 1. Нормализация фото

Двойная нормализация — на клиенте и на входе `ml/`, чтобы SLA и качество не зависели от того, что именно прислал браузер или скрипт организатора.

- **Клиент** (`web`, `useScan`): поворот фото по EXIF, уменьшение до 1600 px по длинной стороне, перекодирование в JPEG качества 0.9 — 150–400 КБ вместо 3–8 МБ с телефона, что критично для SLA на мобильной сети. Реализация — `app/composables/useScan.ts` (за пределами зоны этого файла, см. `web/ARCHITECTURE.md §Поток сканирования`).
- **Сервер `ml/`**: `ImageOps.exif_transpose` (координаты в ответе — уже в повёрнутом изображении), PNG/скриншот с альфа-каналом накладывается на белый фон `#fdfbf6` сайта (а не на чёрный), затем при необходимости уменьшается перед детектором. Скрипт организатора может прислать оригинал 12 Мп без клиентской нормализации — сервер обязан справиться и с ним (`ml/ML_SERVICE.md §2`).

## 2. Извлечение признаков

- **Детекция.** RF-DETR-Seg Small (COCO-класс «bottle», zero-shot, Apache-2.0), сегментирует каждую бутылку на фото. Пост-обработка: dedup по IoU, фильтр по минимальной площади, top-N самых крупных, сортировка слева направо. Из маски оценивается зона этикетки (профиль ширины по строкам — «плечо» бутылки).
- **Главная бутылка (primary).** Одно из двух правил (`PRIMARY_RULE`): бутылка, пересекающая вертикальную центр-линию кадра (`center_line`, по умолчанию — устойчивее к боковым бутылкам на полке), либо максимум `площадь × близость к центру` (`area_center`). Если детектор не нашёл ни одной бутылки (кроп вплотную на этикетку) — псевдобутылка на весь кадр.
- **Кроп и эмбеддинг.** Bbox главной (и остальных показанных) бутылки расширяется на 10 % с каждой стороны и подаётся в SigLIP2 so400m NaFlex (`max_num_patches=1024`) — получается 1152-мерный L2-нормированный вектор. Это тот же рецепт кропа, которым построен индекс каталога и которым модель дообучалась (см. «Текущая модель» в [README.md](README.md)) — рассогласование рецепта на инференсе и на обучении/индексации было главным источником потери качества на ранних этапах.

## 3. Поиск по каталогу

Косинусное сходство вектора кропа к векторам индекса каталога, агрегация по `slug` максимумом (у одного вина может быть несколько векторов — фото карточки плюс, в старых индексах, размеченные ракурсы видео). Top-K кандидатов сортируются по убыванию score → `neighbors`; top-1 и разрыв с top-2 (`margin`) — метрика уверенности, которую отдельно требует ТЗ.

**Решение found / not_found** — по порогу `top1 ≥ FOUND_MIN_COS`, откалиброванному на real-photo так, чтобы доля ложных `found` на вине вне каталога была низкой (`ml/ML_SERVICE.md §7`). Это единственная точка, где сервис явно отказывается гадать: near-duplicates каталога (та же этикетка, другой год/категория/сладость) — единственное, что порог принципиально не решает, поэтому именно на них измеряется итоговая достоверность (см. подмножество `same_line` в `rp_eval`).

Прод-путь — pgvector (PostgreSQL) с HNSW-индексом по косинусу; сейчас, до переезда каталога в БД, индекс — файл `.npy`/`.npz` в памяти процесса (поиск по ~10⁴ векторов укладывается в единицы миллисекунд, узкое место — не поиск, а эмбеддинг). Схема таблицы и то, что кладётся в индекс — `ml/ML_SERVICE.md §5`.

## 4. Выдача карточки

- **Контракт `ml/`.** `POST /recognize` отдаёт полный JSON: верхнеуровневые `status/slug/confidence/read` (копия матча главной бутылки, для обратной совместимости и `/predict`) + `detection.bottles[]` с матчем и координатами каждой найденной бутылки. `POST /predict` — тот же пайплайн, но только `{"slug": "..."}` (или `""`) для скрипта организатора; отдаёт top-1 всегда, даже при `not_found`, потому что в тесте организатора все фото — из каталога, и пустой ответ гарантированно засчитывается как ошибка. Полная схема — `ml/ML_SERVICE.md §3`.
- **Confidence.** `top1`, `margin` и `top5` — в API, не в интерфейсе (прямое требование ТЗ: экран выбора варианта убран из UX именно потому, что метрика достаточно стабильна). Доступно через `/api/predict`-эквивалент напрямую на `ml/`, а полноценно — через `POST /api/wines/search-by-photo`.
- **Одна карточка на сайте.** `server/api/wines/search-by-photo.post.ts` берёт матч главной бутылки (или той, что визуально доминирует — см. `prominence` ниже), достаёт полную карточку из каталога (`server/utils/catalog.ts`) и аналоги (`server/utils/analogs.ts`), и отдаёт сайту единственный JSON без списка кандидатов.
- **Какие бутылки отмечены в UI (prominence).** Если на фото несколько бутылок, сайт (`server/utils/prominence.ts`) решает, что показать: одна явно преобладающая (по площади и близости к центру, разрыв ≥ 2× со второй) — только она, точка + мини-карточка под фото; иначе — весь передний ряд (заметность ≥ 40 % и высота ≥ 60 % от лучшей, до 6 бутылок) — цветные кружки на фото и такие же у карточек в колонке справа. Мелкие бутылки заднего плана не отмечаются никогда. Экрана «какое из вин ваше» нет — ровно то же требование ТЗ, что и про confidence.

## 5. Дополнительный функционал (удержание после поиска)

- **Цифровой сомелье.** Наводящие вопросы (к чему подать, повод) → вердикт по конкретному вину плюс подборка из каталога (`/api/sommelier`, `app/components` сомелье на сайте).
- **Аналоги из других виноделен** (`server/utils/analogs.ts`): цвет, сладость, сорта, регион, рейтинг, не больше одного вина с каждой винодельни, с объяснением совпадения (match % + причины) — закрывает и сценарий `not_found`, и «попробовать похожее» для найденного вина. Ровно то, что в ТЗ помечено как решение, которое «оценивается особенно высоко».
- **Сверка с этикеткой.** Прочитанные `LabelReader`'ом цвет/сладость/год против данных карточки каталога на странице `/wines/:slug` — типовая ошибка покупки («на этикетке полусладкое, в каталоге сухое») ловится прямо в интерфейсе.
- **«Мои вина».** Сохранённые вина и история сканов на устройстве пользователя, без регистрации (`app/pages/my.vue`, `useMyWines`, `localStorage`).

## Границы сервисов (web ↔ ml)

`web` не знает, как устроена модель — только HTTP-контракт `ml/ML_SERVICE.md`, который лежит в отдельном репозитории-подпапке и специально держит поля стабильными («можно добавлять, нельзя переименовывать») именно чтобы фронтенд и матчер менялись независимо. `web/server/utils/catalog.ts` — единственная точка на стороне сайта, которая знает, что каталог сейчас — файл `data/catalog.json`, а не PostgreSQL/Strapi; замена источника каталога на сайте не трогает публичный API. У `ml/` — свой независимый читатель того же `catalog.json` (`ml/app/catalog.py`, путь из `CATALOG_PATH`): ему в любом случае нужен JSON-снимок каталога для сопоставления и построения индекса, так что переезд на БД на стороне сайта саму `ml/` не затронет, только источник экспортируемого `catalog.json` для неё. `ml/` со своей стороны не знает про существование сайта, cards или UI — только про фото на входе и slug/confidence/detection на выходе. Эта граница позволяет параллельную разработку (сайт, ML-пайплайн, обучение моделей) без конфликтов контракта.

## Надёжность

- **Отказоустойчивость по эндпоинтам.** Сайт умеет держать несколько адресов `ml/` одновременно (`NUXT_ML_URL` — список через запятую, плюс файл-оверрайд `ml-url.txt`, перечитываемый на каждом скане — актуально для временных Cloudflare-туннелей с Kaggle/vast.ai). Упавший эндпоинт (таймаут, `502/503/504/530`, обрыв соединения) выводится из ротации немедленно и не ждёт полного таймаута на следующей попытке — при наличии запасного адреса; неретраиваемые ошибки (4xx) пробрасываются как есть.
- **Health-пробы.** Эндпоинт, помеченный «упавшим», проверяется в фоне через `GET /health` каждые 15 с (`server/utils/recognizer.ts`) и возвращается в ротацию сразу, как только отвечает — без перезапуска сайта. `GET /api/ml/status` показывает текущее состояние всех настроенных адресов вручную.
- **Docker healthcheck + автовосстановление.** Оба контейнера объявляют `HEALTHCHECK` (`ml`: `GET /health`; `web`: `GET /api/wines?limit=1`) и `restart: unless-stopped` в `docker-compose.yml` — упавший процесс поднимается заново без ручного вмешательства; `web` в компоуз-файле ждёт `ml: condition: service_healthy` перед стартом.
- **Деградация без обрыва пайплайна.** Нет ни одного настроенного `ml/`-адреса → сайт не падает, а переходит в демо-режим (псевдорезультат по хешу фото). Ошибка внутри `ml/` на `/predict` отвечает `{"slug": ""}` со статусом `200`, а не исключением — чтобы не сорвать прогон скрипта организатора; ошибка сама пишется в лог сервиса.

## Деплой

- **Локально** (без GPU или с Apple Silicon/MPS) — два процесса напрямую (`uvicorn` + `npm run dev`), см. «Быстрый старт» в [README.md](README.md).
- **Docker Compose** — `web` + `ml` одной командой на одной машине, GPU по умолчанию (`docker-compose.yml` → `deploy/docker/Dockerfile.ml-gpu`, CUDA-образ, дообученная модель, веса ~5 ГБ скачиваются с Hugging Face при первом старте); без GPU — оверрайд `docker-compose.cpu.yml` (тот же образ и модель, `DEVICE=cpu`, без резервирования GPU).
- **GPU-сервер (vast.ai)** — одна машина, `ml` слушает только `127.0.0.1`, наружу выходит `web` через Cloudflare-туннель без аккаунта; процессы перезапускаются сами при падении. Полный сценарий — один Jupyter-ноутбук (`deploy/vast/deploy_vast.ipynb`), инструкция — [`deploy/vast/README.md`](deploy/vast/README.md).
- **Kaggle T4** (только `ml/`, для тестирования модели без своего GPU) — `ml/kaggle/serve_t4.ipynb`, подключается к локально запущенному сайту через `web/ml-url.txt`, см. `ml/README.md`.


## Метрики

Реальные фото «у полки», вино есть в каталоге: **F1 0.948, Recall@1 0.961, Recall@5 1.000** (базовая SigLIP 2 без дообучения: 0.838 / 0.868 / 0.981). Замер воспроизводится скриптом `web/scripts/eval_service.py` через `/api/predict` — так же, как это делает скрипт организаторов; для живого демо те же цифры и время ответа показывает скрытая страница `/metrics`. Веса дообученной модели — HF [`dobermanjohn/secret_a`](https://huggingface.co/dobermanjohn/secret_a).


Скорость на RTX 6000 Pro: детектор RF-DETR — 10.8 мс на фото, эмбеддинг SigLIP 2 — 7.1 мс на картинку, путь «фото → эмбеддинг» целиком (детектор + кроп + SigLIP) — 34.2 мс. На RTX 3060 полный ответ сервиса — около 0.43 с; SLA ТЗ — до 3 с.
